Accepted orders,
durable events

A transactional outbox keeps a broker outage from losing the confirmation event for an accepted order.

Make one durable decision

The Orders API writes order_1042 and its outbox event evt_7f3 in one database transaction. Commit persists both. Rollback persists neither. Accepting an order no longer depends on a successful broker call in the request path.

Orders APIOrder + outboxDispatcher

The dispatcher reads only committed events and publishes them to the broker. It marks an event delivered only after the broker acknowledges publication. Here, “delivered” means published to the broker—not that a worker has finished processing it.

During an outage

Without an acknowledgement, the event remains pending. The dispatcher retries publication. The accepted order and the work still to be sent remain in the database.

After a crash

Publishing can succeed before the dispatcher records that success. A crash in this window means the next retry can publish evt_7f3 again.

At-least-once, not exactly-once

Duplicates are part of the contract. The worker must handle them without repeating its database effect. There is no global ordering guarantee; do not infer one from the arrows above.

Make retries safe
at the consumer

Durable publication closes one failure window. An idempotent worker closes the next.

Record the ID with the effect

Use the stable event ID to recognise a retry. Recording evt_7f3 and applying the worker’s database effect must be atomic. Merely checking for an ID before a separate write leaves a race between concurrent deliveries.

  1. Start a database transaction and claim the event ID under a uniqueness constraint.
  2. If the ID was already processed, skip the database effect.
  3. Otherwise apply the effect and commit it with the ID record. Rollback persists neither.

Check the boundaries, not only the happy path

Failure pointExpected result
Before producer commitNeither the order nor its event persists.
Broker unavailableThe outbox event remains pending for retry.
After publish, before marking deliveredA duplicate can reach the worker.
Worker transaction rolls backNeither the database effect nor the processed-ID record commits.

Email is a separate boundary

Database deduplication cannot atomically include an email send. Use evt_7f3 as the provider’s idempotency key, if supported. Without that protection, a crash after sending but before recording success can send the email twice. Other external effects need their own idempotency strategy too.
